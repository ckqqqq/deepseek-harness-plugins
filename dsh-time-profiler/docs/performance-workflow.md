# Long-horizon 任务的计时、分析与优化

## 当前可测量范围

插件通过 agent/assistant-stream 记录主 agent 每次流式模型尝试的开始、首次非空输出、结束，用 performance.now() 计时。区间包含消费和最终提交，不是服务端推理耗时，也不是纯 HTTP 耗时。首次输出可能是 reasoning、text 或工具调用增量，不等同于用户第一次看到正文。辅助模型调用（例如没有主 agent stream 的压缩调用）目前未被独立捕获，仍属于未细分时间。

工具使用 tools/execute waterfall，始终调用 next()，原样返回结果或重新抛出原错误，不改变 signal、调度策略或工具参数。计时起点在调度与前置策略通过之后，包含其它执行中间件、真实工具体及嵌套工作。工具内部网络等待仍属于工具执行经过时间。审批、排队和结果处理不由此区间单独计量。

通过区间边界扫描，整轮时间分为：仅模型、仅工具、模型与工具重叠、其他。四者相加等于单调时钟整轮经过时间。多个工具并发或 run_code 内部嵌套只在时间构成中计一次；工具累计排名则保留每次调用的耗时，因此外层工具与内层工具可能重复累计。

子代理在自己的 session 中记录。父代理等待子代理时，这段时间表现为父代理的工具执行。把父子 session 的经过时间直接相加得到的是 worker 累计时间，不是任务 wall time。

## 任务选择与汇总

任务边界必须由实验定义。一次任务可能跨多个 turn，也可能包含子代理；不能自动认为整个 session 都是同一个任务。将属于该次任务的 turn JSON 文件显式传入：

```sh
cd ./deepseek-harness-plugins/dsh-time-profiler
npm run analyze:task -- /absolute/run-one/turn-1.json /absolute/run-one/turn-2.json
```

输出 activeTime（选中轮次累计）、模型尝试和失败计数、工具执行排名、模型及工具 p50/p95/max 和观察建议。p95 使用 nearest-rank，是本次样本的统计，不代表总体延迟保证。缺少运行时计时的旧报告计入 missingTimingCount，不会填造计时。轮次之间的人类等待不计入 activeTime；多个并发 session 的汇总不能解释为任务 wall time。

## 如何定位下一步优化

| 观察到的现象 | 需要核对的证据 | 可验证的改动 |
| --- | --- | --- |
| 模型累计时间高 | 请求次数、失败尝试、输入长度、首次输出等待与生成时间 | 减少冗余上下文或重复轮次；控制输出预算，检查质量回归 |
| 某工具调用次数高 | 相同任务中是否重复搜索、读取、构建 | 合并请求、复用已有结果；文件变化时正确失效缓存 |
| 单次工具 p95 高 | 网络、子进程、超时、工具数据量 | 缩小查询范围、减少大结果、复用连接；保持工具语义 |
| 工具累计高但经过时间不高 | 并发或外层/内层重叠 | 不依据累计值贸然调整；先看共享时间轴 |
| 工具区间串行 | 调用是否独立，是否有 exclusive 或读写依赖 | 仅对独立操作验证并行执行，不绕过权限与互斥 |
| 其他时间高 | 审批、排队、退避、压缩、持久化尚未细分 | 补充相应扩展点计时后再改动 |

当前唯一对分析工具本身的性能调整，是把 JSON 序列化和 HTML 构建移到 setImmediate 后，再异步写盘，减少在 session/event 同步回调中进行文件构建。事件采集和结束汇总仍有开销，尚未量化真实长任务中的影响；不能声称插件零开销。

## 与 pi、Codex 的实验协议

后续按多类长尾任务测试：跨模块代码修改、定位复杂错误、长时间构建/测试、密集搜索与读取、网络工具失败重试、上下文压缩、子代理并发。这是待建立的任务分类，不是已经完成的 benchmark。

每次运行记录 task id、初始 git commit、输入、harness 版本、模型/推理设置、工具权限、网络与代理、机器环境、超时预算，以及任务验收结果。各产品的原始日志映射到统一 interval：session、turn、step、LLM attempt、tool、outcome。pi 和 Codex 适配器尚未实现；当前插件只采集 dsh。

如果能使用同一模型与相同推理设置，可以研究 harness 对轮次、工具策略和上下文的影响。若 Codex 和 dsh 使用不同模型，差异必须标记为产品整体差异，不能归因于 harness 本身。冷缓存与热缓存分别运行，同一任务多次重复；先比较成功率，再比较成功运行的时间分布、失败和超时。每次只修改一个因素，保留原始报告和验收输出，再决定是否接受优化。
